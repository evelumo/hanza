# Stage 1: canonical model, domain core and sync engine

- **Status:** draft
- **Date:** 2026-10-04
- **Author:** Claude (stage 1 spec agent) for Piotr Graczyk
- **Related:** ADR 0001 (`docs/adr/0001-hanza-owns-stock.md`), ADR 0002 (`docs/adr/0002-state-tables-with-event-log.md`), glossaries `packages/connector-sdk/CONTEXT.md` and `packages/core/CONTEXT.md`, issues #1–#8, roadmap stage 1 in `docs/plan-architektury.html`

## Summary

Stage 1 builds the contract everything else stands on: the final-for-now Connector SDK (canonical Order, Offer and Stock level schemas, capabilities, error taxonomy, conformance test kit), the domain tables and services in the core (Products, Offers, Warehouses, Stock, Reservations, Orders, Connections, Events), a sync engine on the existing `JobQueue` port (pull Offers and Orders, push Available, push Order status), and simple panel screens. A **fake connector** (`@hanza/connector-fake`) proves the whole path end to end without a real Channel. The work ships as four stacked PRs (§10).

## Problem

Today there are only auth, tenancy, a queue round trip and a draft SDK whose `Order` mirrors the Channel's status and whose stock push is keyed by SKU, both of which contradict decisions made since (ADR 0001, glossary). No domain tables exist, so the panel cannot show Products or Orders. Stage 2 (Allegro, WooCommerce) cannot start until the SDK contract and the engine exist.

Non-goals: see §11 (Out of scope).

## Proposed design

### 1. Overview

```
panel (apps/web) ──server actions──▶ core services ──same DB transaction──▶ state tables + event_log
       │                                   │ after commit
       └── requestSync ──▶ JobQueue ◀──────┘ (stock.push, orders.updateStatus)
                              │
worker (apps/worker) ── startWorker ──▶ job handlers (core/src/jobs/*) ──▶ connector capabilities (via registry)
                              ▲
                     sync.tick (every 60 s) enqueues due pulls/pushes per Channel
```

Dependency direction after stage 1:

```
apps/web, apps/worker ─▶ @hanza/connector-registry ─▶ @hanza/connector-fake ─▶ @hanza/connector-sdk ─▶ zod
apps/*                ─▶ @hanza/core ─▶ @hanza/db
                                    └─▶ @hanza/connector-sdk
```

`@hanza/core` never depends on a connector or on the registry; the apps pass connector definitions into `createContext()`.

### 2. Domain rules (normative)

**Order status** is one of `new`, `processing`, `shipped`, `cancelled`. `shipped` and `cancelled` are terminal.

Manual transitions (a person in the panel):

| From | Allowed to | Stock effect |
| --- | --- | --- |
| `new` | `processing`, `shipped`, `cancelled` | to `shipped`: consume; to `cancelled`: release |
| `processing` | `new`, `shipped`, `cancelled` | same as above |
| `shipped`, `cancelled` | none (`DomainError('invalid_transition')`) | — |

A manual change to `shipped` is refused with `DomainError('unmatched_lines')` while the Order has an Unmatched line. Every manual change enqueues `orders.updateStatus` after commit.

Channel facts (applied in `occurredAt` order, then by `id`; each fact id is recorded once per Order):

| Current status | Fact `cancelled` | Fact `shipped` |
| --- | --- | --- |
| `new` | → `cancelled`, release | → `shipped`, consume |
| `processing` | → `cancelled`, release, add reason `cancelled_while_processing` | → `shipped`, consume |
| `shipped` | status unchanged, add reason `channel_fact_conflict` | no change |
| `cancelled` | no change | status unchanged, add reason `channel_fact_conflict` |

A fact-driven change is never pushed back to the Channel. Becoming `cancelled` (either way) removes the reason `shortage`.

**Needs attention** = `order.attentionReasons` is non-empty. Reasons: `unmatched_line`, `shortage`, `cancelled_while_processing`, `channel_fact_conflict`. `unmatched_line` is present exactly while the Order has an Unmatched line (maintained automatically). The other reasons are removed only by a person (`resolveAttention`).

**Line matching** (at import and on rematch): (1) if `offerExternalId` is set and the Offer `(connectionId, offerExternalId)` is linked, use its Product; (2) else if `sku` is set and a Product with exactly that SKU exists in the organization, use it; (3) else the line is an Unmatched line. SKU comparison is exact and case-sensitive; SKUs are trimmed on input.

**Reservation** lifecycle: `open` (on import or line link, Order `new`/`processing`) → `released` (Order cancelled) or `consumed` (Order shipped; Stock decreases by the Reservation's units in the same transaction). One Reservation per Order line, always in the default Warehouse. Linking a line on a `shipped` Order creates a `consumed` Reservation and decreases Stock; on a `cancelled` Order it creates none.

**Shortage**: when a Reservation is made, `availableBefore` is computed under the Stock row lock (§4.4). If `availableBefore < units`, the line gets `shortage = true` and the Order gets the reason `shortage`. The Reservation is made anyway; Available may go below zero.

**Available**(Product) = Σ `stock.units` over all the organization's Warehouses − Σ `reservation.units` where `status = 'open'`. It is computed, never stored. The value pushed to a Channel is `max(0, Available)`.

**Offer linking**: an Offer is linked to at most one Product. `linkedBy` is `sku` (automatic) or `manual`. Automatic linking (on Offer pull, and on Product creation) applies only to Offers with `linkedBy` null or `sku`: an Offer with `linkedBy = null` and a SKU matching a Product is linked; an Offer with `linkedBy = 'sku'` whose SKU changed is relinked by the new SKU or unlinked. A manual link or unlink sets `linkedBy = 'manual'` and automatic linking never touches that Offer again. Linking an Offer (either way) requests a stock push for it. Unlinking does not push anything.

**Rematch**: after `createProduct`, `createProductsFromOffers`, `linkOffer` and an Offer pull that linked at least one Offer, the caller runs `rematchUnmatchedLines` for the organization: Unmatched lines of Orders in `new`/`processing` are matched again by the rules above and linked as if by hand (actor `system`). At most 500 lines per call.

### 3. Data model

Conventions (same as `core.prisma`): ids `String @id @default(uuid(7))`; tables snake_case via `@@map`; columns keep Prisma's camelCase names, so **raw SQL must double-quote every identifier** (`"organizationId"`, `"order"`). Every tenant-owned table has `organizationId`, a relation to `Organization` with `onDelete: Cascade`, and an index starting with `organizationId` (directly or via a unique). `@updatedAt` columns have no database default, so raw `INSERT`s and `UPDATE`s must set `"updatedAt" = now()` themselves. Prisma enums (`OrderStatus`, `ChannelFactType`, `PaymentMethod`) share names with SDK types; both are the same string unions, so core uses the SDK types and aliases Prisma's where it needs them (`import type { OrderStatus as DbOrderStatus } from '@hanza/db'`).

Money is stored as `Decimal @db.Decimal(19, 4)` plus a `Char(3)` currency; services convert to the canonical `Money` with `decimal.toFixed()`. The canonical schema allows at most 15 integer and 4 fraction digits, so every canonical amount fits.

`Organization` in `auth.prisma` gets back-relations only: `products Product[]`, `offers Offer[]`, `warehouses Warehouse[]`, `stock Stock[]`, `reservations Reservation[]`, `orders Order[]`, `orderLines OrderLine[]`, `orderChannelFacts OrderChannelFact[]`, `connections Connection[]`, `syncStates SyncState[]`. Migration: one migration, `pnpm db:migrate --name stage1_domain`, committed under `packages/db/prisma/migrations/`. `@hanza/db` also exports `export type Tx = Prisma.TransactionClient`.

#### Default Warehouse

Lazy get-or-create in core, **not** a Better Auth hook: it works for organizations that already exist (no backfill), in the worker and in tests, and does not touch auth configuration. `ensureDefaultWarehouse(db, organizationId)` runs `INSERT INTO "warehouse" ("id","organizationId","code","name") VALUES (gen_random_uuid()::text, $org, 'default', 'Magazyn główny') ON CONFLICT ("organizationId","code") DO NOTHING`, then selects the row. Every service that touches Stock or Reservations calls it first (outside the transaction is fine; it is idempotent). The panel never shows Warehouses.

#### Idempotency (external ids)

No generic `ExternalRef` table. Each synced row carries its Channel key with a unique constraint: Offer `(connectionId, externalId)`, Order `(connectionId, externalId)`, Order line `(orderId, externalId)`, Channel fact `(orderId, externalId)`, Reservation `(orderLineId)`. Products have no external ids (Hanza owns them). A duplicate insert from a concurrent run fails on the constraint, the job retries and takes the "already exists" path.

#### 4.1 Context, errors, actors

```ts
// context.ts
export interface Context {
  env: Env
  db: Db
  queue: JobQueue
  log: Logger
  secrets: SecretBox            // slice B
  connectors: ConnectorRegistry // slice C
}
export interface CreateContextOptions { env?: Env; connectors?: AnyConnectorDefinition[] } // connectors: slice C
export function createContext(scope: string, options?: CreateContextOptions): Context

// actor.ts
export type Actor = { type: 'user'; userId: string } | { type: 'system' }

// errors.ts — thrown by services for expected failures; the panel maps `code` to Polish copy.
export type DomainErrorCode =
  | 'not_found' | 'sku_taken' | 'invalid_transition' | 'unmatched_lines'
  | 'already_linked' | 'unknown_connector' | 'invalid_config'
export class DomainError extends Error {
  constructor(readonly code: DomainErrorCode, message?: string, readonly details?: Record<string, unknown>)
}
```

`env.ts` adds `HANZA_ENCRYPTION_KEY: z.string().refine((v) => Buffer.from(v, 'base64').length === 32, 'must be base64 of exactly 32 bytes')`.

Rules for every service function:

- First parameters are `(ctx: Context, organizationId: string, …)`. Every Prisma `where` and every raw SQL statement includes `organizationId`. Records are loaded with `findFirst({ where: { id, organizationId } })`, never by id alone; a miss throws `DomainError('not_found')`.
- Writes that matter run in `ctx.db.$transaction(fn, { timeout: 10_000, maxWait: 5_000 })` and append their Events through `appendEvent(tx, …)` inside that transaction (ADR 0002).
- Enqueueing (`requestStockPush`, `orders.updateStatus`) happens **after** commit.
- Raw SQL uses `$queryRaw`/`$executeRaw` tagged templates only.


**Concurrency strategy** (Postgres default READ COMMITTED, no SERIALIZABLE):

1. A transaction that changes Stock or Reservations first locks, in this order: (a) the Order row if one is involved (`SELECT "id" FROM "order" WHERE "id" = $1 AND "organizationId" = $2 FOR UPDATE`), then (b) the Stock rows of all involved Products via `lockStock`.
2. `lockStock` first ensures a Stock row exists for each Product in the default Warehouse (`INSERT … SELECT … ON CONFLICT ("productId","warehouseId") DO NOTHING`), then runs `SELECT "id" FROM "stock" WHERE "organizationId" = $org AND "productId" = ANY($ids) ORDER BY "productId", "warehouseId" FOR UPDATE`. The fixed order (Order row first, Stock rows sorted) prevents deadlocks between Hanza's own write paths.
3. Only after the locks are held does it read Available (`getAvailability(tx, …)`); under READ COMMITTED each statement sees all transactions committed before it, and every writer of these rows is blocked on the same locks, so `availableBefore` is exact.
4. Writes are relative and atomic: `UPDATE "stock" SET "units" = "units" - $n, "updatedAt" = now() WHERE …` for consume; `setStock` writes the absolute value under the same lock.
5. Multiple lines of one Order for the same Product are reserved sequentially, subtracting from `availableBefore` in memory.
6. In the same transaction, `markOffersForStockPush` runs `UPDATE "offer" SET "stockPushSeq" = "stockPushSeq" + 1 WHERE "organizationId" = $org AND "productId" = ANY($ids) RETURNING "connectionId"`.
7. A deadlock or lock timeout surfaces as an error: jobs retry; panel actions show "Spróbuj ponownie".

`OrderRow` = `{ id, externalId, connectionId, connectionName, placedAt, buyerName, total: Money, status, attentionReasons }`. `OrderDetail` = `OrderRow` + `{ payment, buyer: Buyer, shippingAddress: Address, billingAddress: Address | null, lines: Array<{ id, externalId, offerExternalId, sku, name, quantity, unitPrice: Money, productId, productSku, productName, shortage, reservationStatus: 'open' | 'released' | 'consumed' | null }>, facts: Array<{ externalId, type, occurredAt, note, recordedAt }>, events: EventRow[] (latest 50), allowedTransitions: OrderStatus[] }`.

`importOrder` (input already parsed with `orderSchema` by the caller):

1. `ensureDefaultWarehouse`.
2. Transaction: `SELECT … FROM "order" WHERE "connectionId" = $c AND "externalId" = $e AND "organizationId" = $org FOR UPDATE`.
3. If it exists: skip to step 7 (an imported Order is a snapshot; only new Channel facts change it).
4. Otherwise match lines (§2), insert the Order (`status 'new'`) and its lines.
5. `lockStock` for matched Products; `reserveLine(…, 'open')` per matched line in `productId` order; set `shortage` on lines.
6. Reasons: `unmatched_line` if any line is unmatched, `shortage` if any shortage. Events `order.imported`, `stock.reserved` per Reservation, `order.attention_raised` if reasons were added.
7. For each fact in `order.facts` sorted by (`occurredAt`, `id`) whose `(orderId, externalId)` is not recorded: insert `OrderChannelFact`, Event `order.channel_fact_recorded`, apply `factTransition` (release/consume through the same helpers; Event `order.status_changed` with `cause: 'channel_fact'`).
8. `markOffersForStockPush` for every Product whose Reservations or Stock changed. Commit. Then `requestStockPush(connectionIds)`.

`changeOrderStatus`: lock the Order, check `allowedTransitions` and the Unmatched-line rule, release/consume, update status and reasons, Events, mark Offers, commit; then `requestStockPush` and enqueue `orders.updateStatus` `{ organizationId, orderId }` with `coalesceKey: 'orders.updateStatus:' + orderId`.

`linkOrderLine`: lock the Order; the line must belong to the organization and have `productId = null` (else `DomainError('already_linked')`); the Product must belong to the organization. Set `productId`; reserve per §2 (`open` for `new`/`processing`, `consumed` for `shipped`, none for `cancelled`); update `unmatched_line`/`shortage` reasons. If the line has `offerExternalId` and that Offer exists on the Order's Connection with `productId = null`, link the Offer to the same Product with `linkedBy 'manual'`. Events `order.line_linked`, `stock.*`, `offer.linked`. After commit `requestStockPush`.

`resolveAttention`: removes every reason except `unmatched_line`; Event `order.attention_resolved`.

BullMQ mapping (only in `queue.ts`): `coalesceKey` → `deduplication: { id: coalesceKey, keepLastIfActive: true }`; `delayMs` → `delay`; `schedule` → `queue.upsertJobScheduler(scheduleId, { every: everyMs }, { name: job.name, data: job.schema.parse(payload) })`. Default job options stay (5 attempts, exponential 2 s). `apps/worker` no longer imports `bullmq`.

Job refs (`packages/core/src/jobs/refs.ts`, slice B; handlers in slice C reuse them with `defineJob({ ...ref, handler })`):

| Name | Payload (zod) | Coalesce key | Triggered by |
| --- | --- | --- | --- |
| `sync.tick` | `{}` (system job; the only payload without `organizationId`) | — | scheduler, every 60 s |
| `offers.pull` | `{ organizationId, connectionId, trigger: 'schedule' \| 'manual' }` | `offers.pull:<connectionId>` | tick (every 60 min), `requestSync`, `addConnection` |

| `orders.updateStatus` | `{ organizationId, orderId }` | `orders.updateStatus:<orderId>` | `changeOrderStatus` after commit |

All ids are `z.string().min(1)`. Handlers read current state from the database; payloads only identify what to work on, so coalescing never loses information.

What the engine does (implemented in slice C, `packages/core/src/sync/run-connector.ts`):

| Kind | Job outcome | Connection health | `sync_state` |
| --- | --- | --- | --- |
| success | done | → `ok` | `finishSyncRun` |
| `auth_expired` | `PermanentJobError` (no retry) | → `auth_expired` | `failSyncRun` |

```ts

// config/credentials parsed with the connector's schemas (failure → PermanentJobError + health failing);

// log = ctx.log.info with { connectionId, connectorId } added.

// sync/run-connector.ts
runConnectorCall<T>(ctx, scope: { organizationId: string; connectionId: string; stream: SyncStream; run: JobRunInfo }, call: () => Promise<T>): Promise<T>
// applies the table in §5.4; validates nothing itself.

// sync/requests.ts

// sync/schedule.ts

export const SYNC_INTERVALS_MS = { offers_pull: 3_600_000, orders_pull: 120_000, stock_push: 600_000 } as const
```

Handlers (`packages/core/src/jobs/<name>.ts`, registered in `registry.ts` next to `system.ping`). Every handler loads the Connection with `openConnection(ctx, payload.organizationId, payload.connectionId)` and returns without work if it is missing or its connector is not registered (logged), so an `organizationId` that does not own the Connection does nothing.

- **`sync.tick`**: `listConnectionsForTick`; for each Connection whose connector is a Channel and whose health is not `auth_expired`, for each stream in `SYNC_INTERVALS_MS`: if `lastStartedAt` is missing or older than the interval, enqueue the stream's job (`trigger: 'schedule'`) with its coalesce key. Registered by the worker at start: `ctx.queue.schedule('sync.tick', syncTickJob, {}, { everyMs: TICK_EVERY_MS })`.
- **`offers.pull`**: `startSyncRun`; cursor `null`; loop ≤ 50 pages: `runConnectorCall(offers.pull)`, parse every returned Offer with `offerSchema` (a `ZodError` is classified `permanent` by `runConnectorCall`), `upsertOffers(…, seenAt = run start)`, stop when `hasMore` is false. Then `finishSyncRun({ seen, created, updated, linked })`; if `linked > 0`: `rematchUnmatchedLines` and `requestStockPush([connectionId])`. If `trigger === 'manual'`: enqueue `orders.pull { trigger: 'manual' }`. Offers that disappeared from the Channel are left as they are.
- **`orders.pull`**: `{ cursor } = startSyncRun`; loop ≤ 20 pages: `runConnectorCall(orders.pull(cursor))`, parse each returned Order with `orderSchema`, `importOrder` each (in returned order), then `saveSyncCursor(nextCursor)`; stop when `hasMore` is false. If still `hasMore` after 20 pages, enqueue itself (same trigger). `finishSyncRun({ pulled, imported, factsApplied, pages })`. A crash between import and cursor save re-pulls the page; `importOrder` is idempotent.
- **`stock.push`**: `startSyncRun`; loop ≤ 10 batches: `listOffersAwaitingStockPush(limit 100)`; stop when empty; `getAvailability`; levels `{ offerExternalId, sku, available: max(0, available) }`; `runConnectorCall(stock.push(levels))`; `markOffersPushed`. If the 10th batch was full, enqueue itself. `finishSyncRun({ pushed })`. If the connector lacks `stock.push`, return.
- **`orders.updateStatus`**: load the Order (organization-scoped) and its Connection; if the connector lacks the capability, return; `runConnectorCall(orders.updateStatus({ orderExternalId, status: current status }))` with stream `order_status_push`; `finishSyncRun({ pushed: 1 })`.

Connection health transitions (all through `finishSyncRun`/`failSyncRun`, each change with Event `connection.health_changed`):

| From | Event | To |
| --- | --- | --- |
| any | a run succeeds | `ok` |
| any | `auth_expired` error | `auth_expired` |
| any except `auth_expired` | `permanent` error, or `transient` error on the last attempt | `failing` |
| any | `rate_limited`, or `transient` before the last attempt | unchanged |

A Connection leaves `auth_expired` only through a successful manual run (the tick skips it).

`apps/worker/src/index.ts` (slice C): `createContext('worker', { connectors })`, `startWorker(ctx, jobs, { concurrency: Number(process.env.WORKER_CONCURRENCY ?? 10) })`, `schedule('sync.tick', …)`, graceful shutdown as today.

### 9. Decisions made in this spec

1. Order status list is `new`, `processing`, `shipped`, `cancelled`; `shipped` and `cancelled` are terminal.
2. Channel facts are explicit in the canonical Order (`facts[]`, connector-stable ids); stage 1 fact types are `cancelled` and `shipped`.
3. A fact that conflicts with a terminal status is recorded and raises Needs attention instead of moving the status (moving `shipped` → `cancelled` would need Stock to come back).
4. An imported Order is a snapshot; only new Channel facts change it later.
5. Line matching tries the linked Offer first, then the exact SKU.
6. A person cannot set `shipped` while Unmatched lines exist; a Channel `shipped` fact is always applied.
7. Cancelling an Order removes the `shortage` reason.
8. Needs attention is stored as a reasons array; `unmatched_line` is automatic, the others are cleared by a person.
9. Unmatched lines of open Orders are rematched automatically after Product creation and Offer linking.
10. Linking a line on a shipped Order creates a consumed Reservation (Stock decreases); on a cancelled Order, none.
11. The default Warehouse is created lazily by `code = 'default'`; no Better Auth hook.
12. Available is computed (Σ Stock over Warehouses − Σ open Reservations), never stored.
13. Concurrency: READ COMMITTED + `SELECT … FOR UPDATE` on the Order row, then Stock rows sorted by `productId`.
14. No generic ExternalRef table; `(connectionId, externalId)` uniques on each synced table.
15. Stock push uses per-Offer sequence counters bumped in the same transaction, a coalesced per-Connection job, and a 10-minute sweep.
16. One global `sync.tick` scheduler instead of a scheduler per Connection.
17. Connectors are registered in `@hanza/connector-registry`; apps pass them into `createContext()`.
18. Connectors declare `credentialsSchema`; the core seals credentials and hands them decrypted to capabilities; connectors authenticate their own requests (`ctx.fetch` = global fetch + 30 s timeout).
19. Sealed format `v1:iv:tag:ciphertext` with `organizationId` as AAD.
20. `offers.pull` reads every Offer on the Channel on each run; `orders.pull` is an incremental feed with a persisted cursor.
21. A connector output that fails the canonical schema is a `permanent` error.
22. Raw Channel payloads are not stored (they would duplicate unencrypted Buyer data, issue #6).
23. Offers removed on the Channel are not detected; unlinking an Offer pushes nothing.
24. Product SKU is immutable and Products cannot be deleted in stage 1.
25. The fake connector is always registered in stage 1.
26. Money is stored as `numeric(19,4)`; canonical amounts allow at most 4 fraction digits.
27. Buyer addresses are a JSON snapshot validated with `addressSchema`; the canonical address carries `taxId`.
28. BullMQ worker wiring moves into core (`startWorker`); `apps/worker` no longer imports `bullmq`.
29. A rate-limited retry does not consume an attempt and waits at most 15 minutes.
30. Connections in `auth_expired` are skipped by the tick; a manual sync always runs.
31. `EventLog` gains `subjectType`/`subjectId` so a Product's, Order's or Connection's Events can be listed.
32. Channel connectors must implement `offers.pull`, `orders.pull` and `stock.push`; `orders.updateStatus` is optional.
33. DB-backed tests use a fresh database per run created from `HANZA_TEST_DATABASE_URL` and are skipped when it is unset.
34. Glossary: added **Connection health** to `packages/core/CONTEXT.md`.

## Tenant & security considerations

- Every service takes `organizationId`, every query filters by it, records are loaded with `{ id, organizationId }`; panel code gets `organizationId` only from `requireTenant()`. Job handlers load the Connection/Order with the payload's `organizationId`, so a mismatched payload does nothing. The only cross-tenant read is `listConnectionsForTick` (ids, connector id, health, timestamps).
- Credentials: AES-256-GCM with `HANZA_ENCRYPTION_KEY` (32 bytes, base64), AAD = `organizationId`, sealed before insert, opened only in the worker (`openConnection`). Never selected by list/detail queries, never logged, never put into Events, never prefilled in forms. Losing the key makes Connections unusable (sign in again); rotating it is out of scope (the `v1:` prefix leaves room).
- Connector error texts are stored in `sync_state.lastError` (≤ 1000 chars) and shown in the panel; `errorFromResponse` never includes response bodies, and the add-connector skill forbids secrets in error messages.
- Buyer data is personal data stored unencrypted (issue #6); it never goes into Events or logs.
- Input: all action input is zod-validated; connector config/credentials are validated with the connector's own schemas; canonical data from connectors is validated with the SDK schemas before it touches the database.
- Stock correctness: §4.4; the concurrency tests below are part of the gate. Per `AGENTS.md`, the stock/reservation code in slice B needs human review before merge.

Each package with DB tests (`packages/core`, `apps/worker`) has `vitest.config.ts` that loads the root `.env` if present (`process.loadEnvFile`, like `prisma.config.ts`) and sets `globalSetup: ['./vitest.global-setup.ts']`, a one-line file re-exporting `setup`/`teardown`. DB test files are named `*.db.test.ts`, read `inject('hanzaTestDatabaseUrl')` and use `describe.skipIf(!url)`. If the URL is set but the server is unreachable, setup fails with "Start Postgres with `pnpm infra:up` or unset HANZA_TEST_DATABASE_URL". Tests isolate by creating a fresh Organization each (`createTestOrganization(db)`), never by truncating.

`@hanza/core/testing` exports `createTestContext({ databaseUrl, connectors? })` (real `db`, `secrets` with a random key, silent logger, in-memory queue), `createTestOrganization(db): Promise<string>`, and `createInMemoryJobQueue()` which records `enqueued` and `schedules`, honours `coalesceKey` (drops a request while one with the same key waits), and `drain(ctx, jobs, { maxJobs = 200 })` runs jobs FIFO: `RetryLaterError` re-queues at the end, other errors retry immediately up to 5 attempts (`PermanentJobError` stops at once), failures collected in `failed`.

## Rollout / migration

1. Add `HANZA_ENCRYPTION_KEY` (`openssl rand -base64 32`) to `.env`; web and worker refuse to start without it.
2. `pnpm db:deploy` (purely additive migration; no backfill: default Warehouses are created lazily).
3. Deploy the worker (registers `sync.tick`), then web.

Rollback: no production data exists yet; revert the PRs and drop the new tables. Stage 1 is pre-release, so no feature switch.
