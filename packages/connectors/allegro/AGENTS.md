# Allegro connector (`@hanza/connector-allegro`)

The Allegro marketplace (allegro.pl, and the allegro.cz / .sk / .hu Orders that reach the same account). Offers in, Orders in (including Orders still awaiting payment), Stock out, prices out, Order phase out. No shipments or invoices yet. Spec: GitHub issue #82; decisions that bind it: ADR 0015, 0019, 0020, 0021, 0022.

What this file says about Allegro's behaviour comes from the OpenAPI file (`https://developer.allegro.pl/swagger.yaml`) and the tutorials, checked against the sandbox on 2026-10-10: what the sandbox showed is listed under "Verified against the sandbox (2026-10-10)", what could not be produced there under "Still unverified". Check the latter before trusting a behaviour that depends on one.

## Layout

- `src/settings.ts`: installation settings, config, credentials, hosts, `User-Agent`.
- `src/client.ts`: `request` (never throws on a status), `send` (throws the connector error), `parse` (zod, issue paths only), `errorCodeOf`, `concurrently`.
- `src/auth.ts`: the device flow and refresh (`allegroAuth`).
- `src/api/*`: zod schemas of the responses, only the fields the mapping reads (everything else, PESEL and `messageToSeller` included, is stripped).
- `src/mapping/*`: pure mappers (Offer, Order, Order update, Channel facts, phase → fulfillment status).
- `src/cursor.ts`: the Order feed cursor.
- `src/capabilities/*`: one file per capability, and `offer-edit.ts`: the Offer `PATCH` and its per-Offer answers, shared by `stock.push` and `price.push`.
- `src/testing/`: test tooling only (`@hanza/connector-allegro/testing`): the API simulation, sample payloads, the scrub config. `src/index.ts` never exports it.

## Sign-in and tokens

- **Installation settings** (one registered application per Hanza, Allegro forbids asking sellers for a Client ID): `HANZA_CONNECTOR_ALLEGRO_CLIENT_ID`, `_CLIENT_SECRET`, `_ENVIRONMENT` (`production` default, or `sandbox`), `_APP_NAME` (must equal the registered application name: it goes into the `User-Agent`). Changing the Client ID means signing in again on every Connection.
- **Hosts.** Production: API `https://api.allegro.pl`, OAuth `https://allegro.pl/auth/oauth`. Sandbox: API `https://api.allegro.pl.allegrosandbox.pl`, OAuth `https://allegro.pl.allegrosandbox.pl/auth/oauth`. `deviceFlow.verificationHosts` lists both sites (`allegro.pl`, `allegro.pl.allegrosandbox.pl`), since it is static and the environment is a setting.
- **Device flow, start.** `POST {oauth}/device?client_id=<id>`, `client_id` in the query and no body, `Authorization: Basic base64(clientId:clientSecret)`, `Accept: application/json`. No `scope`: the scopes registered with the application apply (`OAUTH_SCOPES` in `settings.ts` lists what to register: orders read/write, sale offers read/write, profile read).
- **Device flow, start answer.** `verification_uri` is `<site>/uzytkownik/bezpieczenstwo/skojarz-aplikacje`, `verification_uri_complete` the same with `?code=<user_code>`; user codes are 8 lower-case letters; `expires_in: 3600`, `interval: 5`.
- **Device flow, poll.** `POST {oauth}/token`, form body `grant_type=urn:ietf:params:oauth:grant-type:device_code&device_code=…`, Basic auth. `400 authorization_pending` / `slow_down` / `access_denied` / `expired_token` map to the SDK's poll states; any other OAuth error is a `PermanentError` (`400 invalid_request`, "Invalid device code", for an unknown code). Tokens last 12 h (`expires_in: 43199`). On approval `GET /me` gives the account (`id`, label = `login`).
- **Refresh.** `grant_type=refresh_token`; both tokens rotate. The spent refresh token is still accepted right after the rotation (60 s, per the tutorial) and the old access token keeps working until it expires, so a refresh whose answer was lost can be sent again within that time. A `400` with `invalid_grant` or `invalid_token` is `AuthExpiredError` (sign in again); any other OAuth error is `PermanentError`. The core decides when to refresh (ADR 0020).
- **A 401 from the token endpoint** (device start, poll or refresh: `invalid_client`, "Client authentication failed") refuses the application, not the seller: a wrong client id or secret. It is `PermanentError('401 Unauthorized: check the installation settings')`, never `AuthExpiredError`, since signing in again cannot fix it. A 401 from the API (`/me` included: `invalid_token` with a `WWW-Authenticate: Bearer …` header for a bad token, `unauthorized` without one) stays `AuthExpiredError`.
- **Every API request**: `Accept: application/vnd.allegro.public.v1+json`, `Content-Type` the same on a JSON body, `User-Agent: <appName>/<version> (+https://github.com/evelumo/hanza)`, `Authorization: Bearer <accessToken>`.

## Rate limits

Published: 9,000 requests a minute per Client ID (production and sandbox), over it the Client ID is blocked for a minute with 429; plus an unpublished leaky bucket per seller on some resources. Declared: `application: 6000 / 60 s`, `connection: { concurrency: 3 }`. Inside one call at most 3 requests are in flight (`ENDED_BY_LOOKUP_CONCURRENCY`, `CHECKOUT_FORM_CONCURRENCY`, `OFFER_EDIT_CONCURRENCY` for stock and price pushes). A 429 is `RateLimitedError` with `Retry-After` when present, else the SDK's 60 s, which matches Allegro's one-minute block.

## `offers.pull`

- `GET /sale/offers?limit=1000&offset=<n>&publication.status=ACTIVE&publication.status=ACTIVATING&publication.status=ENDED` (drafts, `INACTIVE`, left out). Cursor = next offset; `hasMore = offset + count < totalCount`. Offset paging can shift while Offers appear; the next hourly pull catches up and the upsert absorbs duplicates.
- One Fulfillment Offers (`isFulfillment: true`) are dropped in the mapper (not filtered in the query: whether `isFulfillment=false` filters is unverified).
- Mapping: `externalId = id`, `sku = external.id`, `url = <site>/oferta/<id>`, `price = sellingMode.price` for `BUY_NOW` / `ADVERTISEMENT` (null for an auction, or when it does not fit `Money`), `status`: `ACTIVE`/`ACTIVATING` → `active`, `ENDED` → `ended`. Prices are kept as Allegro writes them: the listing drops a trailing zero (`"24.0"`, `"34.5"`), which `Money` accepts.
- **`endedReason`.** The listing has no `endedBy`. An `ENDED` Offer with stock left cannot have sold out: `other`, no call. One with stock 0 (or none reported) is looked up with `GET /sale/product-offers/{id}`: `publication.endedBy === 'EMPTY_STOCK'` → `sold_out`, anything else → `other`; a 404 there leaves `endedReason` out, so Hanza never reopens it.

## `orders.pull` (ADR 0021)

**Cursor.** Opaque text, two phases, fields URI-encoded and joined by `:` (`src/cursor.ts`):

- `l1:<eventId>:<boughtBefore>:<lastBoughtAt>` while listing the Orders open at the start;
- `e1:<eventId>:<boughtBefore>` in the journal.

`eventId` is an Allegro event id (a decimal integer, growing with time, e.g. `1791663869066571`), empty for a seller whose journal was empty at the start (`GET /order/event-stats` answers `latestEvent: null`); the journal is then read without `from`. `boughtBefore` is the frozen boundary, kept for ever.

**Cursor null.** `GET /order/event-stats` first (journal position), then `boughtBefore` = the time of that answer, from its `Date` header (Allegro's clock: the boundary is compared with Allegro's purchase times, so a skewed local clock would move Orders across it); the local clock only when the header is missing or unreadable. The other way round, an Order placed between the two moments would be neither listed nor sent in full.

**The purchase time** the feed compares and pages by is a form's **latest** `lineItems[].boughtAt` (`boundaryKeyOf`), in both phases: it is what the `lineItems.boughtAt` filters compare ("Latest line item bought date"), and with one key a form whose lines were bought on both sides of the boundary is either listed or sent in full, never neither. The Order's `placedAt` stays the earliest.

**Listing.** `GET /order/checkout-forms?limit=100&sort=lineItems.boughtAt&lineItems.boughtAt.lte=<boughtBefore>&lineItems.boughtAt.gte=<max(lastBoughtAt, boughtBefore - 30 days)>`.

- **No status filters in the query.** The OpenAPI types `status` and `fulfillment.status` of this resource as a single `string` (unlike `publication.status` of `/sale/offers`, an array), so a repeated value is not supported (a server may keep only the last one). The open ones are picked in code: a form is kept unless `status === 'CANCELLED'`, `fulfillment.status` is `SENT`, `PICKED_UP` or `CANCELLED`, or it is One Fulfillment. The simulation honours only the last value of a repeated single-valued parameter, so the tests prove nothing relies on repeating one.
- **Window: `LISTING_WINDOW_DAYS = 30`.** An Order open at connect time is listed only if it was bought at most 30 days before the boundary. Older open Orders (an unpaid one Allegro has not cancelled yet, an Order the seller left unshipped for a month) are not imported; their later journal entries arrive as updates, which the core ignores.
- **Keyset, never offset**, on the purchase time above. The next page starts at `gte` the last key, so the forms sharing it come again (harmless, imports are idempotent) and an Order closing between pages cannot shift the next page. A page that is not full, or a full page whose key did not move (more than 100 Orders bought in the same instant: would loop for ever), ends the listing; its `nextCursor` is the `e1:` cursor with `hasMore: true`. A full page counts every form on it, closed ones too.
- Listed forms become full Orders, `BOUGHT` ones included (Allegro already reserved their units): with the Buyer's account address until the delivery address appears. A form with no usable address at all cannot be a canonical Order (`orderSchema` requires a shipping address; an SDK limit, issue #101): it is sent as an Order update instead (which the core ignores for an Order it does not have) and its form id is logged.

**Journal.** `GET /order/events?from=<eventId>&limit=100` (`from` is exclusive: the events after it), then `GET /order/checkout-forms/{id}` for each distinct form of the page (events without `order.checkoutForm` are skipped, but still move the cursor). `nextCursor` = `e1:` with the page's last event id; `hasMore` = the page had 100 events; an empty page returns the same cursor with `hasMore: false`. Per form, one item at most (so a full Order and an update of the same Order never share a page):

- latest `lineItems[].boughtAt` **after** `boughtBefore` → a full Order with every fact it has now; when the form is `READY_FOR_PROCESSING`, followed right after it on the page by an Order update of the same form (facts and addresses), because the core takes addresses only from an update: a full Order it already has only adds facts, so without it a paid Order would keep the account address it was imported with while unpaid;
- otherwise an Order update (`kind: 'update'`, the facts, and the shipping and billing addresses when the form is `READY_FOR_PROCESSING`): the core applies it only to an Order it imported, so an Order closed before the Connection is never imported;
- `404` → an update with one fact `{ id: '<formId>:removed', type: 'cancelled', occurredAt: <the form's last event time on the page>, note: 'Merged into another order on the Channel' }` (a merged purchase).

**Skipped:** One Fulfillment forms (`fulfillment.provider.id === 'ALLEGRO'`), in both phases; in the journal, `BOUGHT` / `FILLED_IN` forms with no usable address (neither `delivery.address` nor `buyer.address` with street, city, postal code and country: they come again on a later event). A journal form after the boundary with no usable address that is past checkout (paid, or cancelled before it was ever filled in) goes as an Order update and its form id is logged, as in the listing (issue #101). Such a paid Order is then not imported; not expected in practice (a paid form always has an address).

**Unpaid Orders** (ADR 0015). `BOUGHT` / `FILLED_IN` prepaid forms are Orders with `awaitingPayment: true`, shipped to the Buyer's account address until the delivery address appears at payment. Once paid, the form carries a `paid` fact; before the boundary that arrives as an update with the delivery address, after it as the full Order again followed by that update.

**Expired cursor.** The journal never expires a position. `from` must be an integer in [0, 2^63 - 1]: anything else (`-1`, a UUID, text) answers `422 VALIDATION_ERROR` (`path: getOrderEvents.from`). Any integer is accepted, also one no event has: one past the latest event, or far before the first, answers `200 {"events":[]}`. So an old position simply returns the events still kept after it (the journal keeps 60 days), and the feed cannot get stuck unless its cursor holds an id Allegro never issued, which the connector never writes. The rule stays as a guard: a `400`, `404` or `422` from `GET /order/events` for a request that carried `from` is `CursorExpiredError` when its body is an Allegro error body (`errors[]` with at least one `code`); only the 422 was seen. The same statuses without such a body (a proxy's page, an empty answer) go through `errorFromResponse` (`PermanentError`). The core restarts the feed from null and records it. Reading the statuses this broadly is safe: the core turns a second `CursorExpiredError` in one run, or one for cursor null, into a permanent failure, so a query wrong for another reason cannot loop. Without `from` (a seller whose journal was empty at the start) those statuses stay `PermanentError`; any other failure keeps its class.

## Order status, both directions

Inbound (Channel facts, ids stable per Order, notes always null):

| Fact | When | `occurredAt` |
| --- | --- | --- |
| `<id>:paid` | prepaid, and `payment.finishedAt` set or `status === 'READY_FOR_PROCESSING'` (never for cash on delivery) | `payment.finishedAt`, else `updatedAt` |
| `<id>:shipped` | `fulfillment.status` is `SENT` or `PICKED_UP` | `updatedAt` |
| `<id>:cancelled` | `status === 'CANCELLED'` or `fulfillment.status === 'CANCELLED'` | `updatedAt` |
| `<id>:removed` (type `cancelled`) | the form answers 404 | the event's time |

`READY_FOR_PICKUP`, `SUSPENDED` and `RETURNED` give no fact. Hanza never mirrors Allegro's status.

Outbound (`orders.updateStatus`): `PUT /order/checkout-forms/{id}/fulfillment` with `{ "status": … }` and no `checkoutForm.revision` (Hanza owns the phase; a revision would turn every Buyer edit into a 409): `new` → `NEW`, `processing` → `PROCESSING`, `shipped` → `SENT`, `cancelled` → `CANCELLED`. 204 is done, whatever the status before (Allegro takes `NEW` after `SENT`, `PROCESSING` after `CANCELLED`); an unknown form answers `422 SellerOrdersStoreUnprocessableEntityException`, and 404 and 422 are `PermanentError`. `CANCELLED` only sets the seller's label; it refunds nothing.

## `stock.push` (ADR 0022)

One `PATCH /sale/product-offers/{offerId}` with `{ "stock": { "available": n } }` per level, at most 3 in flight, 0 included (0 ends an active Offer). Allegro applies the publication side of an edit after it answers (seconds later on the sandbox), so an answer never shows the ending or the reopening it causes: a 200 shows the new stock with the publication as it was, a 202 the Offer as it was. A result for every level:

- 200 / 202 and `n = 0` → `ended` (the Offer is sold out: an active one ends with `endedBy: EMPTY_STOCK` seconds later, an ended one stays ended), unless the answer shows `publication.status: 'INACTIVE'`: a draft keeps 0 and stays a draft (`ok`);
- 200 / 202 and `n > 0` → `ok`, unless the answer shows `publication.status: 'ENDED'` (the stock is set, but an ended Offer stays ended): then if `endedBy` is `EMPTY_STOCK` a second `PATCH` `{ "publication": { "status": "ACTIVE" } }` reopens it, else `rejected` with `OFFER_ENDED_<endedBy>` (e.g. `OFFER_ENDED_USER`): an Offer the seller or an admin ended stays ended;
- the reopen `PATCH` answers 202 (`Location: …/operations/<uuid>`, `Retry-After: 120`) with the Offer as it was (still `ENDED`), and the Offer is `ACTIVE` seconds later; on an Offer already active it answers 200. Either is `ok`, whatever the body shows; a 400 / 403 / 404 / 422 there is `rejected` as below;
- a 409 on that reopen `PATCH` → `rejected` `OFFER_REOPEN_PENDING` (an earlier edit still being processed; the stock is set, the reopen is tried again on the next push). Never seen on the sandbox: a reopen sent right after a stock-0 edit answered 202, and the Offer ended anyway. Kept as a guard;
- 404 → `rejected` `OFFER_NOT_FOUND` (an unknown numeric id; a non-numeric one answers `400 InvalidOfferIdInPathException`, which the 400 rule rejects with that code); 400 / 422 → `rejected` with the body's first `errors[].code` (`REJECTED` when it has none that is a plain code);
- 403 → `rejected` `FORBIDDEN` (an Offer of another account), unless every level of the call answered 403: then a missing scope is the likelier cause, and the call fails with `PermanentError`;
- 409 on the stock `PATCH` ("the previous edition is still being processed", documented, never seen) → `TransientError` for the whole call: the retry pushes every level again, which is harmless;
- 401, 429, 5xx → the usual error classes for the whole call. An empty array sends nothing.

A 202 whose body does not parse is taken as accepted: `ended` for a 0, `ok` above it.

A known race, from the asynchronous ending: a number above 0 pushed while a 0 pushed just before is still ending the Offer answers `ACTIVE` (`ok`), and the Offer ends anyway. Hanza recorded the 0 as `ended`, so the next push to that Offer reopens it.

Possible optimisation, not used: one body with both `{ "stock": { "available": 2 }, "publication": { "status": "ACTIVE" } }` answers 202 and reopens an Offer with stock 2 in one request.

## `price.push`

Hanza owns prices (ADR 0011): `offers.pull` reports `sellingMode.price` as the Offer's price, and `price.push` sets the one Hanza sends. One `PATCH /sale/product-offers/{offerId}` with `{ "sellingMode": { "price": { "amount": "<amount>", "currency": "<currency>" } } }` per price, at most 3 in flight, the amount and currency exactly as Hanza gives them (the currency `offers.pull` reported; no `GET` first). It sets the buy-now price on the Offer's base marketplace (`allegro-pl`); the prices of additional marketplaces (`additionalMarketplaces`) are left to Allegro. A result for every price:

- 200 / 202 → `ok`, whatever the body shows (a 202 shows the Offer as it was; a body that does not parse is accepted all the same);
- 400 / 422 → `rejected` with the body's first `errors[].code` (`REJECTED` when it has none that is a plain code), e.g. `IncorrectBaseCurrency` for a currency the marketplace does not use, `PriceBelowMin` below 1.00 PLN, `VALIDATION_ERROR` for more than two decimals;
- 404 → `rejected` `OFFER_NOT_FOUND`; 403 → `rejected` `FORBIDDEN`, unless every price of the call answered 403: then the call fails with `PermanentError` (a missing scope);
- 409 → `TransientError` for the whole call (documented for Offer edits, never seen on a price edit); 401, 429, 5xx → the usual error classes for the whole call. An empty array sends nothing.

The sandbox's answers: a 200 echoing the Offer with the amount written with two decimals (`"25"` → `"25.00"`, `"21.50"` → `"21.50"`), on an active Offer and on an ended one alike (an ended Offer takes the price and stays ended); the listing (`GET /sale/offers`) shows the new price some seconds later, as a double (`"21.5"`, `"25.0"`). EUR on an allegro.pl Offer answers `422 IncorrectBaseCurrency` (`path: prices[0].price.currency`), `"0.00"` `422 PriceBelowMin`, `"19.999"` `422 VALIDATION_ERROR` (`path: sellingMode.price.amount`), an unknown id `404 OfferNotFoundException`. A price edit right after a stock edit or a reopen of the same Offer answered 200 (no 409).

## Errors

- `GET /order/events` with `from`: 400, 404 or 422 with an Allegro error body → `CursorExpiredError` (see "Expired cursor"; the sandbox answers 422 only, for a `from` that is not an integer). Every other non-2xx a capability does not handle itself goes through `errorFromResponse`: 401 → `AuthExpiredError`; a bare 403 stays `PermanentError` (no right to that resource, not signed out: conformance C14); 429 → `RateLimitedError`; 408 / 5xx → `TransientError`; other 4xx → `PermanentError`. A network failure or timeout is `TransientError`; a `ConnectorError` from `ctx.fetch` (the core's rate limiter) passes through unchanged.
- A body that cannot be read (the connection reset, the 30 s timeout firing mid-body) is `TransientError` with the cause, for API and token-endpoint answers alike; a `ConnectorError` raised while reading passes through; a body that is not JSON fails its schema (`PermanentError`).
- Messages never hold a body, a token or Buyer data: only the status, and for a body that fails its schema the issue paths. Only `errors[].code` (and the OAuth `error`) is ever read from an error body, never `message` or `userMessage`.

## Verified against the sandbox (2026-10-10)

Seller account `Hanza` (id `111578766`) on `api.allegro.pl.allegrosandbox.pl`, an application registered in the sandbox developer portal.

- **Auth.** The device flow end to end (start without `scope` and without a body, `authorization_pending` before approval, tokens after, `GET /me`); the verification URI path; `invalid_request` for a bogus device code; `invalid_grant` for a bogus refresh token (`AuthExpiredError`); `invalid_client` 401 for a wrong secret on the token and device endpoints (`PermanentError`); the API's 401 bodies; refresh rotates both tokens, the spent refresh token still works right after, the old access token until it expires. A password change on the seller's account revokes every token at once: the API answers `401 invalid_token` ("Access token expired", although `exp` is in the future) and the Connection must sign in again (`AuthExpiredError`, as the connector already maps it).
- **Offers.** The listing's `publication` has `status`, `startingAt`, `startedAt`, `endingAt`, `endedAt`, `marketplaces` and no `endedBy`; its `stock` is `{available, sold}`, the detail's `{available, unit}`; prices are strings, sometimes without the trailing zero. The detail of an unknown numeric id answers 404, of a non-numeric id `400 InvalidOfferIdInPathException`. The Offer URL `<site>/oferta/<id>` opens the Offer page. An Offer the seller ends shows `ENDED` / `endedBy: USER`, and a push to it is `rejected OFFER_ENDED_USER`.
- **Stock.** A 0 on an active Offer answers 200 still `ACTIVE`, and the Offer is `ENDED` / `EMPTY_STOCK` seconds later (so `EMPTY_STOCK` is what Allegro records when the application sets 0, and Hanza reopens such Offers). A number above 0 on an `EMPTY_STOCK` Offer answers 200, sets it and leaves the Offer ended; the reopen answers 202 showing the old publication, and the Offer is active seconds later; a reopen of an active Offer answers 200. A reopen right after a stock-0 edit answered 202 (no 409), and the Offer ended anyway. Both fields in one body answer 202 and reopen. An unknown Offer id answers 404.
- **Prices.** A price `PATCH` answers 200 with the amount written with two decimals, on an ended Offer too; the listing shows the new price seconds later, as a double; EUR on an allegro.pl Offer answers `422 IncorrectBaseCurrency`, a price below 1.00 PLN `422 PriceBelowMin`, three decimals `422 VALIDATION_ERROR`, an unknown Offer 404. Detail in "`price.push`".
- **Order journal.** Event ids are decimal integers growing with time; `from` is exclusive; `from` outside [0, 2^63 - 1] or not an integer answers 422; an integer past the latest event answers an empty page, one before the first event returns every event kept after it; `limit` over 1000 answers 422. `GET /order/event-stats` answers `latestEvent: null` on an empty journal. Every answer carries a `Date` header. A purchase gives `BOUGHT` and `FILLED_IN` (possibly the same `occurredAt`), then `READY_FOR_PROCESSING` when paid (cash on delivery: `BOUGHT`, then `READY_FOR_PROCESSING` at once); a seller's fulfillment change gives `FULFILLMENT_STATUS_CHANGED`. Every event had `order.checkoutForm` (`id`, `revision`) and `order.lineItems[]`.
- **Checkout forms.** Ids are UUID v1; any other id answers `422 Not valid time UUID`. A paid form is `READY_FOR_PROCESSING` with `payment.finishedAt` and `paidAmount`; `lineItems[].price` is the unit price after discounts (2 × 39.99 + 5.99 delivery = 85.97); `buyer.address` uses `postCode`, `delivery.address` `zipCode`; the Buyer e-mail is a relay address (`…@user.allegrogroup.pl`). An unpaid form (`FILLED_IN`) has no `payment.finishedAt`, no `paidAmount`, no `delivery.address`, and has `buyer.address`: mapped to an Order awaiting payment shipped to the account address. `orders.pull` from null, from a journal cursor before the purchases and from one after them gave the items described in "`orders.pull`". The listing query the connector sends answers 200.
- **Later purchases** (2026-10-10 22:12–22:17Z, `sandbox-orders-journal-lifecycle`, `sandbox-orders-listing-now`):
  - *Payment after import.* The Order imported awaiting payment, paid later, gives `FILLED_IN` twice, then `READY_FOR_PROCESSING` at `payment.finishedAt`; the form then has `delivery.address` and `paidAmount`. Before the boundary it is an update with the `paid` fact and the delivery address.
  - *Buyer cancellation.* `BOUGHT`, `FILLED_IN` (same `occurredAt`), then an event of its own, `BUYER_CANCELLED`. The form is `CANCELLED` with `payment.finishedAt: null`, `paidAmount: null`, `delivery.address: null` (method and cost still set), `fulfillment.status` still `NEW`, and `updatedAt` the cancellation's time. Mapped to a `cancelled` fact at `updatedAt`, shipped to the Buyer's account address: a full Order after the boundary, an update before it. The listing (no status filter) answers it and the connector drops it.
  - *Cash on delivery.* `BOUGHT`, then `READY_FOR_PROCESSING` at once (no `FILLED_IN`), with `payment: {type: 'CASH_ON_DELIVERY', provider: null, finishedAt: <the purchase time>, paidAmount: null}`, although nothing was paid. So `finishedAt` alone never means paid: the connector gives the `paid` fact only to a prepaid form (any `payment.type` but `CASH_ON_DELIVERY`); the cash-on-delivery Order has no fact and `awaitingPayment: false`.
  - *Invoice.* `invoice: {required: true, address: {street, city, zipCode, countryCode, company: {name, ids: [{type: 'PL_NIP', value}], vatPayerStatus: 'NOT_APPLICABLE', taxId}, naturalPerson: null}, dueDate: null, features: null}`: `company.taxId` repeats the NIP of `ids[]` (both scrubbed by path). Mapped to the billing address, `taxId` from `ids[]` (`PL_NIP` first). Without an invoice: `{required: false, address: null, …}`.
  - *Pickup point.* A parcel-locker form (method "Allegro Paczkomaty InPost") has `delivery.pickupPoint: {id, name, description, address: {street, zipCode, city, countryCode}}`, `id` the locker code (`POZ17A`), and still a `delivery.address` with the Buyer's name and phone.   - *Several lines.* One form with two `lineItems` from two Offers (39.99 + 24.00 + 5.99 delivery = 69.98) is one Order with two lines.
- **Fulfillment.** `PUT …/fulfillment` answers 204 for every status in any order (`NEW` after `SENT`, `PROCESSING` after `CANCELLED`); an unknown form answers 422. `GET /order/checkout-forms` shows a fulfillment change only some seconds after the `PUT` answered 204 (a form set `NEW` right before still listed as `SENT`); the form itself (`GET /order/checkout-forms/{id}`) showed it at once.

## Still unverified

What the sandbox could not produce. Each is an assumption the code makes.

- A 403 on one Offer's `PATCH` meaning "not your Offer", and a 403 on every Offer meaning a missing scope (no foreign Offer could be produced).
- A 409 on an Offer edit while an earlier one is processed (documented, never seen; the 409 rules are guards). A 202 on a price edit (never seen; taken as accepted).
- What the price of an Offer listed on additional marketplaces (allegro.cz / .sk / .hu) does when the base price changes, and what a price edit answers for an auction (never sent: `offers.pull` reports no price for one).
- `Retry-After` (or any rate-limit header) on Allegro's 429: not documented; the SDK reads it when present, else waits 60 s. The sandbox did not answer 429 to 12 000 `GET /me` in 33 s (150 in flight), so the published 9 000-a-minute block could not be observed there.
- A merged form answering 404 (mapped to a `removed` cancellation), and whether a `READY_FOR_PROCESSING` form can still be merged.
- Whether line and total currencies always match on allegro.cz / .sk / .hu Orders (the mapper fails the page with `PermanentError` if not).
- Whether `isFulfillment=false` filters One Fulfillment Offers out of `GET /sale/offers` (not used: the mapper drops them).
- What a form or an event past the journal's 60 days looks like (`from` with an integer far before the first event returned every event kept, as assumed for a position older than 60 days).
- That `sort=lineItems.boughtAt` sorts by the same latest `boughtAt` the filters compare, with a stable order for equal times, and that `status` and `fulfillment.status` of `GET /order/checkout-forms` are single-valued (the connector depends on neither).
- What `delivery.address` of a pickup-point form holds: the sandbox Buyer's account street is the locker's, so whether Allegro puts the Buyer's address or the locker's there (with the Buyer's name and phone) could not be told. Until issue #126 Hanza ships to it as to any address.
- That a `READY_FOR_PROCESSING` prepaid form without `payment.finishedAt` is paid (the `paid` fact then takes `updatedAt`), and that a paid form always has a usable address (else it is sent as an update and not imported, see "Skipped").
- Whether reopening an Offer costs a listing fee, and what a seller's `CANCELLED` does beyond the label.
- A refused device code (`access_denied`): the sandbox's approval page offers no refuse button (only "Dalej" / "Kontynuuj"), so the `denied` state is covered by the simulation only.
