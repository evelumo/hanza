# Organizations define Order statuses as labels within the fixed Order phases

Status: amends ADR 0003 (its first consequence)

Sellers want their own fulfilment workflow ("Waiting for packaging", "Delivered"), but Reservations, Stock consumption, Channel facts, Needs attention and the status push all depend on a small fixed list (issue #1). We decided that list becomes the **Order phases**, unchanged, and that an organization defines **Order statuses** as records that each belong to exactly one phase; every phase has a default status, created on first use. The core only ever reasons about the phase: a move within a phase changes the label and records an Event, nothing else (no Stock effect, nothing sent to the Channel, #29's pending-push mark untouched), while a change of phase follows ADR 0003 exactly. Connectors and the SDK keep speaking phases, so the connector contract does not change.

## Decisions within it

- **Storage.** `order.phase` (the old `status` column, renamed) stays the source of truth; `order.statusId` sits next to it with a composite foreign key `(organizationId, phase, statusId) → order_status(organizationId, phase, id)`, so the database refuses a status of another organization or another phase. A status's organization, phase and id never change.
- **Locking.** The only non-partial unique index on `order_status` covers those immutable columns; one default per phase is a partial index and unique active names an expression index on `lower(name)` (case-insensitive, kept in the migration only: Prisma cannot express it and leaves it alone). Postgres treats columns of non-partial unique indexes as key columns, and updating one would lock the row `FOR UPDATE` and wait behind every Order import holding `FOR KEY SHARE` on it. Writers that give an Order a status lock it `FOR KEY SHARE` while reading it, so a status deleted meanwhile is skipped instead of failing the write.
- **Transitions.** A person may move an Order to any active status of the same phase (in every phase, final ones included) or of a phase `allowedTransitions` allows (ADR 0003); every phase rule goes through `allowedTransitions`, so the others hold for statuses too: an Order awaiting payment (ADR 0015) may change its status within phase new but leave new only to cancelled. Everything else that depends on where an Order is reads the phase: the retention clock `closedAt` (ADR 0016) starts when the phase becomes shipped or cancelled, so moving shipped → "Delivered" does not restart it; a Reservation moves to another Warehouse (ADR 0017) only in phase new or processing; cancelling clears `shortage` and `unmatched_line`. An import or a Channel fact uses the Connection's **Status mapping** for that phase if it names an active status, otherwise the phase default. No per-status rules.
- **Names.** A default status has no name until a person gives it one, and is shown as the phase's name in each person's language: there is no organization locale, and defaults are created by the migration and by the worker. Only a default may have its name emptied, and the panel refuses a phase's name (in any language it speaks) for a status, since it would look like the default.
- **Deleting.** A default status cannot be deleted. A status in use needs an active replacement of the same phase. One transaction deactivates it, marks it as being deleted (`replacedById`, a foreign key of the same organization and phase, and `deletionDueAt`) and moves its Status mappings, with Events; the worker then moves its Orders in batches (`orderStatuses.delete`) and deletes it. While the mark is set, the replacement can be neither deleted nor deactivated (the foreign key refuses the delete too), the status cannot be activated again, and a Status mapping to it is refused: the mapping reads the status `FOR SHARE`, so it waits for a deletion in progress. Each round of the job moves any mapping still on the status, and falls back to the phase default if the replacement was disabled behind the services. `sync.tick` enqueues every deletion whose due time passed (a lost enqueue per ADR 0010, a job that kept failing), at most once per 10 minutes each.
- **History.** Events store the status id, its name at the time and its phase, next to the phases of the change, so renaming never rewrites history and an unnamed default is shown in the viewer's language.
- **Rollout.** The migration holds an ACCESS EXCLUSIVE lock on `order` for its whole run (rename, a full-table UPDATE, NOT NULL, an index, a foreign key), and code from before it fails against the new schema and the reverse: stop web and worker, migrate, then start the new version.

## Considered options

- Statuses as free data with no phase: the core would need per-status Stock semantics, and every connector a mapping table; both are larger and riskier.
- Status mapping of raw Channel-native statuses as data: changes the SDK contract (connectors would return the Channel's own status); left for later (issue #76).
- A JSON mapping on the Connection: no foreign key, so a deleted or foreign status could be referenced.

## Consequences

- An organization that never opens the settings sees the same four statuses as before, in its own language.
- Channels never learn the finer statuses, only phase changes.
- Custom transition rules and per-status permissions (#75), automations and notifications (#77) and Stock behaviour tied to a status (#78) are follow-ups; the SDK still calls the phase `OrderStatus` (#79).
