Hanza — plan architektury

Open source'owy, AI-native hub integracji e-commerce (alternatywa dla base.com) · wersja 5 · 2026-10-04

TLDR

Budujemy mały, stabilny rdzeń w TypeScripcie (kanoniczny model danych + silnik synchronizacji) i konektory jako wymienne paczki o identycznym układzie plików — tak, żeby agent AI dopisywał kolejny marketplace według jednego przepisu i sam sprawdzał wynik testami kontraktowymi.

Z Open Mercato bierzemy konwencje i Next.js, ale nie cały stack: Prisma zamiast MikroORM, pnpm + Turborepo, bez kontenera DI. Dokładamy to, czego CRM nie potrzebuje: osobne workery, kolejkę i testy zgodności konektorów. Licencja MIT, self-host jako pierwszy model wdrożenia.

Koszt/ryzyko: pierwszym konektorem jest Allegro — ma środowisko testowe i przewidywalne API, więc MVP jest realne szybko. Prawdziwym kosztem pozostaje utrzymanie konektorów i poprawność stanów magazynowych.

2 · Co czyni projekt AI-native

Jeden przepis na konektor

Każdy konektor ma identyczne pliki i deklaruje capabilities. Agent nie projektuje — wypełnia szablon.

Pętla zwrotna bez człowieka

Zestaw testów zgodności + nagrane odpowiedzi HTTP. Agent wie, że skończył, gdy pnpm test:connector allegro jest zielone — bez prawdziwych kluczy.

Kontekst w repo, nie w głowie

AGENTS.md z task routerem („dodajesz kuriera → czytaj X”), specyfikacje w .ai/specs/, gotowe skille w .ai/skills/.

Typy jako barierki

zod jako jedyne źródło prawdy, strict TS, lint pilnujący granic: konektor nie może importować bazy ani innego konektora.

Komenda = API = tool AI

Jedna definicja defineCommand generuje endpoint REST, narzędzie MCP i wpis w audycie. Nowa funkcja jest od razu dostępna dla agentów.

AI w produkcie, ale na smyczy

Mapowanie kategorii/parametrów, opisy ofert, diagnoza błędów synchronizacji. Każdy zapis wymaga karty zatwierdzenia (wzorzec z Open Mercato).

Tak wygląda konektor

packages/connectors/allegro/
├── connector.ts        # defineConnector({ id, auth, capabilities })
├── auth.ts             # OAuth / klucze — tylko deklaracja, sekrety trzyma rdzeń
├── client.ts           # klient HTTP + limity zapytań
├── capabilities/
│   ├── orders.pull.ts      # zewnętrzne → kanoniczne Order
│   ├── stock.push.ts       # kanoniczny Stock → zewnętrzne
│   ├── offers.push.ts
│   └── notifications.ts    # webhooki lub odpytywanie dziennika zdarzeń
├── mapping.ts          # czyste funkcje: obcy JSON ⇄ model kanoniczny
├── fixtures/           # nagrane odpowiedzi API (do testów bez kluczy)
├── connector.test.ts   # odpala wspólny zestaw testów zgodności
└── AGENTS.md           # pułapki tego konkretnego API

Rdzeń odkrywa konektory automatycznie (pnpm generate buduje rejestr). Panel sam rysuje formularz konfiguracji ze schematu zod — konektor nie zawiera UI.

4 · Co bierzemy z Open Mercato, a co dokładamy

bierzemy
  • Ze stacku: Next.js, zod, Redis
  • Układ modułu: src/modules/<modul>/ z auto-discovery (schema.prisma, api/, pages/, acl.ts, events.ts, ai-tools.ts, setup.ts)
  • AGENTS.md z task routerem — główny i per paczka
  • Spec-first: .ai/specs/RRRR-MM-DD-tytul.md przed większą zmianą
  • .ai/skills/ i listy Always / Ask first / Never
  • Zatwierdzanie mutacji wykonywanych przez AI
  • Integracje zawsze w osobnej paczce, nigdy w rdzeniu
  • tenant_id + organization_id w każdej tabeli, szyfrowanie pól z danymi osobowymi
dokładamy / pomijamy
  • Worker jako pierwszoplanowy proces — u nas serce to synchronizacja w tle, nie żądania HTTP
  • Connector SDK + testy zgodności jako główny mechanizm jakości
  • Limity zapytań per konto, kursory, idempotencja, dead-letter w panelu
  • Wąski rdzeń: nie budujemy CRM-a, custom entities ani workflowów dokumentów
  • Bez Meilisearch na start — wyszukiwanie w Postgresie
  • Bez MikroORM i Awilix — Prisma i jawne składanie usług

5 · Kolejność budowy

0

Fundament repo i konwencje mechaniczne

Monorepo, CI, Docker Compose, AGENTS.md, szablon specyfikacji, lint granic między paczkami.

Efekt: docker compose up stawia pusty panel z logowaniem.

1

Rdzeń: model kanoniczny + silnik synchronizacji kluczowe decyzje

Tu powstaje kontrakt, na którym stanie wszystko inne. Robimy powoli i ręcznie.

Co dokładnie
  • Encje: Product, Variant, Offer (wystawienie w kanale), Order, StockLevel, Shipment, Invoice, Connection
  • Tabela powiązań external_ref (nasze ID ⇄ ID w kanale) — bez niej nie ma idempotencji
  • Event log + outbox: zmiana stanu i zdarzenie w jednej transakcji
  • Joby: kursor na połączenie, retry z backoffem, limit zapytań per konto, dead-letter widoczny w panelu
  • Surowy payload z kanału zapisywany obok danych kanonicznych (debug + ponowne mapowanie)
  • Connector SDK: defineConnector, defineCapability, zestaw testów zgodności
2

Pierwszy pionowy przekrój: Allegro weryfikuje kontrakt

Zamówienia z Allegro do panelu, stany magazynowe z panelu do Allegro. Konektor pisany ręcznie, razem z drugim, prostym kanałem (WooCommerce) — dopiero dwa pokażą, czy SDK jest dobre.

Co Allegro wymusza w rdzeniu
  • OAuth z odświeżaniem tokenów; tryb „device flow” pasuje do self-hostu (nie wymaga publicznego adresu zwrotnego)
  • Zamówienia przez dziennik zdarzeń odpytywany kursorem, nie webhooki — kursor per połączenie w rdzeniu
  • Limit zapytań per aplikacja — limiter w Redisie
  • Oferty wymagają kategorii i parametrów Allegro — później dobre pole dla AI-mapowania
  • Środowisko sandbox — nagrywamy z niego odpowiedzi do testów zgodności

Efekt: realnie używalne MVP dla polskiego sprzedawcy.

3

Test tezy AI-native: trzeci konektor pisze agent punkt kontrolny

Skill add-connector + generator pnpm create-connector. Agent dostaje dokumentację API (np. InPost) i ma dowieźć zielone testy bez dotykania rdzenia.

Jeśli musi ruszać rdzeń — poprawiamy SDK, zanim konektorów będzie dziesięć.

7 · Ryzyka

Utrzymanie konektorów

API marketplace'ów zmieniają się bez pytania. Odpowiedź: testy zgodności w CI, cotygodniowy test „na żywo” na kontach sandbox, agent otwierający PR z poprawką.

Poprawność stanów magazynowych

Wyścigi = sprzedaż towaru, którego nie ma. Odpowiedź: rezerwacje w transakcji, idempotentne joby, to nie jest kod do pisania przez agenta bez przeglądu.

Dostęp do API Allegro

Przy self-hoście każdy użytkownik rejestruje własną aplikację w Allegro — trzeba to dobrze poprowadzić w onboardingu. Do sprawdzenia: aktualne wymogi weryfikacji aplikacji i limity dla niezweryfikowanych.

Rozrost rdzenia

Base.com to setki funkcji. Odpowiedź: twarda zasada — wszystko, co da się zrobić konektorem lub automatyzacją, nie trafia do rdzenia.
